Mohar · how each part actually works

Mechanisms

Sixteen features. For each: the idea in one line, the mechanism underneath, and the words to use for it.

How to read this

Every section has the same three parts. In one line is what you say first. How it works is the mechanism. Terms is the vocabulary — use these words and the answer sounds like you built it, because you did.

01Signing a record

In one line Each device has a private key. When it records something, it signs it, and anyone can later prove which device said it.

How it works

We use Ed25519, a public-key signature scheme on the Edwards25519 curve. Each device holds a 32-byte private key (the seed); its 32-byte public key is registered in the device table at enrolment. Signing produces a 64-byte signature over the message bytes.

Ed25519 rather than ECDSA for one specific reason: it is deterministic. ECDSA needs a fresh random nonce per signature, and a weak random number generator leaks the private key. A cheap microcontroller signing offline is exactly where that goes wrong. Ed25519 derives its nonce from the message and the key, so there is no nonce to get wrong.

We sign the canonical message bytes directly, not a hash we computed ourselves. Ed25519 hashes internally; signing our own hash would let a caller substitute any 32 bytes for a real message.

Terms

TermMeaning
Ed25519Signature scheme, Edwards curve, 128-bit security level
seed / private key32 bytes held only by the device
public key32 bytes, registered at enrolment, safe to publish
deterministic signatureNo per-signature randomness needed
nonce reuseThe ECDSA failure mode Ed25519 avoids entirely

02Canonicalisation

In one line Two computers must agree byte-for-byte on what was signed, or every signature fails.

How it works

A signature covers bytes, not meaning. The same record written twice can come out with its fields in a different order — after a database round trip, a queue, or a clone — and the signature no longer verifies over the new bytes.

So we use RFC 8785, the JSON Canonicalization Scheme (JCS). It fixes two things: object keys are sorted by UTF-16 code unit, and number formatting is pinned to ECMAScript Number::toString. The bytes become a function of the value alone.

Two rules fall out, and both are load-bearing:

  • Optional fields are omitted, never null. {"a":null} and {} are different byte strings. The signing helper throws on any null before it signs.
  • Timestamps carry exactly three fractional digits and end in Z. 04:30:00Z and 04:30:00.000Z are the same instant and different bytes.
Where this cost real work

The ESP32 has no JCS library. The firmware emits records already in canonical form — keys pre-sorted, integers only, no nulls, no geo field — and signs those exact bytes. A runtime guard aborts any record whose keys go out of order, because the alternative is a device that looks healthy and whose every record is rejected in the field.

Terms

TermMeaning
canonicalisationOne value, exactly one byte representation
RFC 8785 / JCSThe standard that defines it for JSON

absent vs nullDifferent bytes; we always omit

03The hash chain

In one line Each record carries a fingerprint of the record before it, so changing an old one breaks every one after it.

How it works

Two hashes, because they answer two different questions.

bodyHash  = SHA256( JCS(body) )
chainHash = SHA256( prevChainHash ‖ bodyHash )

‖ is byte concatenation. The first record uses a genesis hash of 32 zero bytes as its predecessor.

The device signs only bodyHash's input. It cannot sign chainHash, because it does not know what came before — the chain is global and the device may have been offline for hours. The ledger binds the record to its position when it accepts it.

Verification then proves two independent things:

  • Authorship — the signature verifies over the body, so that device really said it
  • Order and completeness — recomputing the chain proves nothing was reordered, inserted or removed

Concurrency

The chain has exactly one tail. Two writers reading the same prevHash would fork it, so appends take a transaction-scoped advisory lock in the database and serialise. The lock releases on commit or rollback.

TermMeaning
SHA-256Cryptographic hash, 256-bit output, collision-resistant

04Append-only storage

In one line The database does not grant our application permission to update or delete a record. It is not a promise in code; it is a privilege that does not exist.

How it works

Migrations run as a migrator role that owns the schema. The application connects as a separate role which is granted only SELECT and INSERT on the event table — no UPDATE, no DELETE.

On boot the service queries the catalogue for its own privileges. If it finds a connection holding UPDATE or DELETE on the event table, or a superuser connection, it refuses to start. The guarantee is checked at runtime rather than assumed.

Why this framing matters

Application code can be changed by whoever deploys it. A database grant cannot be changed by the application itself. Putting the guarantee at the privilege layer means the strongest claim in the system does not depend on the weakest layer.

Terms

TermMeaning

fail-closed startupRefuse to run rather than run unsafely

05Merkle anchors

In one line Each day's records are summarised into one hash, so any single record can be proved to belong to that day without showing the rest.

How it works

A Merkle tree is a binary tree of hashes. Leaves are the records; each internal node is the hash of its two children; the top is the Merkle root. One root summarises the whole day.

To prove one record is in that day you supply an inclusion proof — the sibling hashes along the path from that leaf to the root, about log₂(n) hashes. The verifier recomputes upward and compares to the published root. A thousand records need roughly ten hashes to prove one.

Leaf hashes and internal hashes use different domain prefixes. Without that separation an attacker could present an internal node as if it were a leaf — a second-preimage attack on the tree.

Partly built

The root is computed and stored. RFC 3161 timestamping — having an external timestamp authority countersign the root, so the date cannot be backdated even by us — is not implemented. The Integrity page says so.

06Splitting the key

In one line The content key is split into four pieces; any three rebuild it, and fewer than three are useless.

How it works

Shamir's Secret Sharing over the finite field GF(2⁸). To split a secret with threshold k=3, you build a random polynomial of degree k−1 = 2 whose constant term is the secret, then evaluate it at four distinct points. Those four values are the shares.

Any three points determine a degree-2 polynomial uniquely — that is Lagrange interpolation — so three shares recover the constant term. Two points determine nothing: every possible secret remains equally likely. This is information-theoretic security, not computational. It does not depend on any problem being hard.

The sharp edge

Shamir does not verify reconstruction. Feed it three shares where one is corrupted and it returns a wrong secret with no error. Here that means an AEAD decryption failure minutes before an exam, with no indication of which holder supplied bad material.

So every share carries a commitment — a hash recorded when the package was sealed — and reconstruction is verified against a commitment to the secret itself. A bad share can be named.

Terms

TermMeaning
Shamir Secret SharingThreshold splitting of a secret
threshold (k-of-n)3-of-4 here
GF(2⁸)The finite field the arithmetic runs in

information-theoreticSecure regardless of computing power

07The time lock

In one line One share of the key does not exist until the exam time. It cannot be leaked, stolen or demanded, because there is nothing yet to take.

How it works

drand is a distributed randomness beacon. Its quicknet chain emits a signed value every 3 seconds, each identified by a round number. Round numbers are pure arithmetic on the clock — round 1 was emitted at a known genesis time, so any future round maps to a known instant.

Timelock encryption uses the beacon's public key to encrypt toward a future round. The ciphertext can only be opened once that round's signature is published — which happens on schedule and cannot be hurried. The scheme is built on BLS signatures and pairing-based identity encryption; the round number plays the role of the identity.

We pin the chain hash, public key, period and genesis time in the code. A beacon that reports different constants is either a different chain or a hostile response, and we want a loud failure rather than a silently retargeted lock.

Why this is the one genuinely preventive piece

Every other control is detective — it records what happened. This one makes early release impossible rather than merely detectable, and it does so with mathematics rather than policy.

TermMeaning
drandDistributed randomness beacon network
quicknetThe chain we target, 3-second period
roundOne beacon output; maps to an exact instant
timelock encryptionEncrypt toward a future round
BLS signaturePairing-based scheme the beacon uses
pinned constantsChain hash and genesis fixed in code

08Custody keys

In one line A credential for one stage of one package, valid for one six-hour epoch, stored only as a hash.

How it works

An epoch is a six-hour slice of the clock. Validity is arithmetic on the timestamp, not a scheduled job — so if rotation never runs, keys stop working rather than keeping working. Fail-closed, not fail-open.

When a key is issued the plaintext appears once, in that response, and nowhere else. Only its SHA-256 and a short fingerprint are stored. Verification hashes what was presented and compares. A database dump yields no usable key.

Keys are stage-scoped: a key for the transit stage does not open the unlock stage. And the engine matches against every key ever issued for that package, not just the current one — so a stale credential (key_expired) is distinguishable from one we never issued (key_unknown). Those call for very different responses.

Terms

TermMeaning

stage-scopedBound to one custody stage
fingerprintShort prefix of the key hash, safe to display
fail-closedFailure denies rather than permits
key rotationIssuing the new epoch's keys

09The access engine

In one line Twenty-one checks, all evaluated, none skipped, and the attempt is written before the answer is returned.

How it works

Deny by default. A request starts refused; every check must positively pass. There is no path that returns granted without having evaluated all of them.

No short-circuiting. We never stop at the first failure. An attempt that trips four checks is a different event from one that trips a clock skew, and there is no second chance to observe an attempt that already happened.

Evidence, not verdicts. Each check records what was observed — “312 m from the centre, geofence is 150 m” — not the word “failed”. A verdict without its inputs cannot be re-examined years later.

Write-before-answer. The attempt is inserted inside the same transaction that produces the decision, before the response is sent. There is no ordering in which a caller learns the outcome without the attempt being on record.

Two design decisions worth naming

A denial is HTTP 200. A refusal is a successful evaluation that produced “no”. A client treating it as a transport error would retry it as though the request had failed to arrive.

Fixed devices are located by binding. The geofence proves the requester is at the centre. A phone must produce a position fix. A station bolted to the wall and bound to its centre at enrolment is located by that binding — demanding a fix from a device with no GNSS could only be satisfied by inventing a number.

10Fingerprint matching

In one line The reader matches on its own chip and returns a slot number and a score. No biometric ever leaves it.

How it works

The R307 module contains its own processor and flash. Enrolment captures two impressions, extracts a feature template (minutiae — ridge endings and bifurcations) from each, merges them into a model, and stores that model in a numbered slot on the module.

Matching captures an impression, extracts features, and searches the stored templates. It returns the matching slot id and a confidence score (roughly 0–255). That is the entire output. The microcontroller never sees an image or a template.

So the ledger records "slot 3 matched, score 187". A breach of the database cannot leak a biometric that was never in it. Under India's DPDP Act 2023 biometric data is personal data, and the cleanest compliance position is not to hold it.

Who slot 3 is

Kept in a separate register — reference data, not chain data. A mapping recorded against the wrong person must be correctable; a signed record must not. Retired mappings are kept, because an assertion signed last month refers to whoever held the slot then. Resolution is therefore as-at-the-time, not as-at-now.

Honest limit

An optical sensor is vulnerable to a presentation attack — a lifted print in gelatin or wood glue. A capacitive sensor resists this considerably better. This establishes that a body was present, not which body.

TermMeaning

11The two-person rule

In one line Two different enrolled templates, inside a short window, or the ceremony is refused.

How it works

The station runs a small state machine. The first accepted match opens a session with a generated identifier and starts a co-presence window of 120 seconds. The second match must fall inside it and must be a different slot.

Three outcomes, and all three are recorded:

OutcomeCause
two_person_confirmedTwo distinct slots inside the window
same_finger_twiceThe same slot presented again
window_expiredThe second official never arrived

One person tapping twice is not two people — the same principle the ledger enforces when it refuses a co-signature from the signing device itself.

A two-second cooldown follows each accepted match. The reader will read the same thumb again if it shifts and settles, and that second read would land as a second assertion. A genuine second official cannot present inside two seconds, so nothing legitimate is suppressed.

The limit worth stating

The rule checks two distinct templates, not two distinct people. If one person enrols two of their own fingers under two names, it passes. That is an enrolment-process failure, and the two photographs are the control against it.

12Photographic commitment

In one line We commit the hash of the photograph to the chain, and keep the photograph somewhere else.

How it works

On a successful match, one frame is captured and encoded as JPEG. We compute SHA-256 over the encoded bytes — not the canvas pixels, because the JPEG is the artefact that will later be re-hashed. That digest goes into the record; the image does not.

This is a commitment scheme, and it gives three properties:

  • The chain proves the image is the one captured at that instant
  • The chain does not become a photo archive
  • Losing the image later does not break the chain — one commitment simply becomes uncheckable

The record also carries assertionEventId, binding the frame to one specific fingerprint assertion rather than merely to the session. So “which official is this a photograph of” has an answer that does not rely on timestamp ordering.

Event scoping

The camera fires only on a biometric assertion — never on a timer, never on motion, never on request. That is purpose limitation made structural rather than promised: a handful of frames per exam of two officials performing one duty, not hours of a corridor.

Terms

TermMeaning
commitmentPublish a hash now, reveal the artefact later
bindingThe committer cannot later swap the artefact
event-scoped captureRecording triggered by one event, not continuous
purpose limitationDPDP principle: collect only for a stated purpose

13Heartbeat and silence

In one line Every device reports in every thirty seconds. The absence of a heartbeat is itself a recorded event.

How it works

Each heartbeat carries a monotonic sequence number held in the chip's non-volatile storage, so it survives a reboot. Gaps are visible: if the ledger holds 41 then 44, two records existed and did not arrive — a different fact from two records never having been made.

A separate watchdog service derives silence. If a monitor misses three consecutive heartbeats it signs a MONITOR_SILENT event. One per outage, not one per poll: a control room drowning in repeats stops reading them.

Why a device cannot report its own silence

MONITOR_SILENT is a service-only kind — the ledger refuses it from a field device. A device that could declare itself silent could also decline to. The asymmetry is the whole point: unplugging the device is not a way to go dark, it is a way to raise an alarm.

14Device identity

In one line Every device is enrolled with its public key. Revoking one invalidates nothing it already signed.

How it works

Provisioning generates a keypair on the machine doing the provisioning and registers only the public half. The private key never crosses the network. The ledger refuses a duplicate public key: one key enrolled as two devices would let a single board sign as both parties to a two-person act.

Revocation sets a timestamp. It stops future records being accepted; it does not retroactively invalidate past ones, because those were validly signed at the time. Rewriting the past is exactly what the system exists to prevent.

The gap, stated on the page itself

Attestation is accepted but not verified. There is no Android Keystore root-of-trust check, so enrolment trusts whoever can reach the endpoint. The Devices page calls this a real gap rather than a simplification, and it is why the service must stay behind a gateway that has not been built.

15Time on the device

In one line The device keeps its own clock and never corrects it from the network. Drift is a finding, not a defect to hide.

How it works

A DS3231 real-time clock is temperature-compensated and battery-backed, so it keeps time with no power and no network. Timestamps are RFC 3339 UTC with exactly three fractional digits — the format the signed body requires.

The ledger records the device's time and its own arrival time separately, and computes clock_skew_ms. It never reconciles the two. A device that quietly rewrote its clock to match a server would destroy the evidence that the two ever disagreed.

If the RTC reports it lost power, the device raises that condition into the ledger at boot rather than carrying on with a wrong clock silently.

16Durability on the device

In one line A record is durable before any radio is touched. Cutting power delays a record; it does not erase one.

How it works

The firmware builds and signs the record, writes it to a spool, and only then attempts to transmit. With a card fitted the spool is an append-only file per day with a cursor marking the first unacknowledged record — nothing is ever deleted, so the card holds the device's own copy of everything it said.

The transport honours three status codes, and each means something different:

CodeMeaningAction
201AppendedDrop from the spool
200DuplicateDrop — this is what makes retry safe
422RejectedDrop and raise; retrying forever wedges the queue

Idempotency comes from a client-generated event id. A device replaying its queue after a flaky sync gets 200 duplicate rather than creating a second copy.

Our build is degraded, and says so

No card is fitted, so the spool is a RAM ring of forty records. It does not survive a power cut, and a long outage overruns it — dropping the oldest record and counting the loss. The device announces spool_absent into the ledger on every boot, because a device running degraded must be distinguishable in the record from one running properly.
